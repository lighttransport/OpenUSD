# Custom Namespace Build for USD v26.05

This document describes how to build USD v26.05 with a custom Python package name (e.g., `pxr_lte`) to enable side-by-side installation with another USD build.

## Summary

The custom namespace build allows you to:
- Install USD with a different Python package name (e.g., `pxr_lte` instead of `pxr`)
- Use a different C++ namespace (e.g., `pxr_lte` instead of `pxr`)
- Use a different library prefix (e.g., `lte_` instead of `usd_`)
- Import both standard USD (`pxr`) and custom namespace USD (`pxr_lte`) in the same Python process

## Key CMake Options

| Option | Description | Example |
|--------|-------------|---------|
| `PXR_SET_EXTERNAL_NAMESPACE` | C++ namespace for USD symbols | `pxr_lte` |
| `PXR_LIB_PREFIX` | Prefix for library names | `lte_` |
| `PXR_PYTHON_PACKAGE_NAME` | Python package directory name | `pxr_lte` |

## Build Procedure (Windows)

### Prerequisites

- Visual Studio 2022 with C++ workload
- Python 3.11 or 3.12 (via uv or other installer; both are verified working — see [Python Version Notes](#python-version-notes))
- TBB (pre-built or from source)
- CMake 3.20+

### Using the Repo Build Scripts (Recommended)

On this branch (`v26.05-custom-namespace`), the patches described below are already applied, and the manual steps in [Step 1](#step-1-clone-and-checkout-v2605)-[4](#step-4-build-and-install) are wrapped by ready-to-run scripts at the repo root. This is the recommended path — it auto-detects Python, validates TBB, and prints a working `pxr_lte` import snippet at the end.

1. **TBB** (one-time, if not already built): `build-tbb.bat all`
   Installs to `..\dist-tbb-reldeb` relative to the repo.

2. **Python with dev headers** (one-time per version): `setup-uv-python-dev.bat [3.11|3.12]`
   Installs a UV-managed CPython with `include\Python.h` and `libs\python3XX.lib` present (UV's default managed Python builds already include these). Defaults to 3.11 if no version is given.

3. **Configure**: `configure-usd-lte.bat [clean]`
   Auto-detects a `cpython-3.11*` install under `%USERPROFILE%\AppData\Roaming\uv\python`. To build against a different version (e.g. 3.12), set `UV_PYTHON_DIR` to the target install directory before running the script:
   ```bat
   set UV_PYTHON_DIR=%USERPROFILE%\AppData\Roaming\uv\python\cpython-3.12.12-windows-x86_64-none
   configure-usd-lte.bat clean
   ```
   Pass `clean` to wipe `build-lte-sameproc` first — required when switching Python versions, since the CMake cache pins the Python paths from the prior configure.

4. **Build + install**: `build-usd-lte.bat all`
   Builds and installs to `..\dist-usd-lte-v26.05`. Use `build-usd-lte.bat build` / `build-usd-lte.bat install` to run either step alone.

There is also a monolithic variant (`configure-usd-lte-monolithic.bat` / `build-usd-lte-monolithic.bat`), installing to `..\dist-usd-lte-monolithic-v26.05`.

### Manual Procedure (from scratch on an unpatched checkout)

If instead you're applying these patches to a fresh Pixar checkout rather than using this branch:

#### Step 1: Clone and Checkout v26.05

```bash
git clone https://github.com/PixarAnimationStudios/OpenUSD.git
cd OpenUSD
git checkout v26.05
```

#### Step 2: Apply Custom Namespace Patches

The following files need to be modified to support custom Python package names:

1. **cmake/defaults/Options.cmake** - Add `PXR_PYTHON_PACKAGE_NAME` option
2. **cmake/macros/Private.cmake** - Patch Python source files to use custom import paths
3. **cmake/macros/Public.cmake** - Patch moduleDeps.cpp to register modules with custom package name
4. **cmake/macros/patchModuleDeps.py** - Helper script for patching moduleDeps.cpp
5. **cmake/macros/genModuleDepsCpp.cmake** - Rewrite the `pxr.` prefix in auto-generated moduleDeps.cpp (see [Two Code Paths in v26.05](#two-code-paths-in-v2605))

#### Step 3: Configure CMake

```bash
mkdir build-lte
cd build-lte

cmake .. ^
    -G "Visual Studio 17 2022" ^
    -A x64 ^
    -DCMAKE_INSTALL_PREFIX=C:/path/to/dist-usd-lte-v26.05 ^
    -DPXR_SET_EXTERNAL_NAMESPACE=pxr_lte ^
    -DPXR_LIB_PREFIX=lte_ ^
    -DPXR_PYTHON_PACKAGE_NAME=pxr_lte ^
    -DTBB_ROOT_DIR=C:/path/to/tbb ^
    -DPXR_BUILD_IMAGING=OFF ^
    -DPXR_BUILD_USD_IMAGING=OFF ^
    -DPXR_BUILD_USDVIEW=OFF ^
    -DPXR_BUILD_TESTS=OFF ^
    -DPXR_BUILD_EXAMPLES=OFF ^
    -DPXR_BUILD_TUTORIALS=OFF ^
    -DPXR_ENABLE_MATERIALX_SUPPORT=OFF
```

#### Step 4: Build and Install

```bash
cmake --build . --config Release --parallel
cmake --build . --config Release --target install
```

### Python Version Notes

Both Python 3.11 (3.11.14) and Python 3.12 (3.12.12), installed via `uv python install`, have been verified to configure, build, and pass the test procedure below without any source changes. `configure-usd-lte.bat`'s auto-detection only globs for `cpython-3.11*`, so building against 3.12 (or any other version) requires setting `UV_PYTHON_DIR` explicitly as shown above — this is a limitation of the auto-detect glob, not of the CMake build itself, and was left as-is since overriding the env var is a one-line workaround. `setup-uv-python-dev.bat` already accepts any version as its first argument (default `3.11`), so no change was needed there either.

## Usage

### Python Import

```python
import sys
import os

# Add DLL directories (Windows Python 3.8+)
os.add_dll_directory(r'C:\path\to\dist-usd-lte-v26.05\lib')
os.add_dll_directory(r'C:\path\to\dist-usd-lte-v26.05\bin')
os.add_dll_directory(r'C:\path\to\tbb\bin')

# Add Python path
sys.path.insert(0, r'C:\path\to\dist-usd-lte-v26.05\lib\python')

# Import custom namespace USD
from pxr_lte import Usd, Sdf, Tf

# Check version
print('USD version:', Usd.GetVersion())  # (0, 24, 11)
```

### Same-Process Dual USD

You can import both standard USD and custom namespace USD in the same Python process:

```python
import sys
import os

# Setup paths for pxr_lte
os.add_dll_directory(r'C:\path\to\dist-usd-lte-v26.05\lib')
os.add_dll_directory(r'C:\path\to\dist-usd-lte-v26.05\bin')
sys.path.insert(0, r'C:\path\to\dist-usd-lte-v26.05\lib\python')

# Import both
from pxr import Usd as PxrUsd      # Standard USD (e.g., from pip)
from pxr_lte import Usd as LteUsd  # Custom namespace USD

print('pxr version:', PxrUsd.GetVersion())
print('pxr_lte version:', LteUsd.GetVersion())
```

## Testing / Verification Procedure

After `build-usd-lte.bat all` completes, run these checks in order — each one validates a different part of the custom-namespace patching, and later ones exercise more of the build than earlier ones.

### 1. Basic import and namespace sanity

```python
import os, sys
os.add_dll_directory(r'C:\path\to\dist-usd-lte-v26.05\lib')
os.add_dll_directory(r'C:\path\to\dist-usd-lte-v26.05\bin')
os.add_dll_directory(r'C:\path\to\tbb\bin')
sys.path.insert(0, r'C:\path\to\dist-usd-lte-v26.05\lib\python')

from pxr_lte import Usd, Sdf, Gf, Tf
print(Usd.GetVersion())        # (0, 26, 5)
print(Usd.__name__)            # 'pxr_lte.Usd'

stage = Usd.Stage.CreateInMemory()
prim = stage.DefinePrim("/World/Sphere", "Sphere")
attr = prim.CreateAttribute("radius", Sdf.ValueTypeNames.Double)
attr.Set(2.5)
assert attr.Get() == 2.5
assert "def Sphere" in stage.GetRootLayer().ExportToString()
```

The important extra check beyond a plain smoke test is a **cross-module `Tf.Type` lookup that forces lazy module loading**, since this is what actually exercises `moduleDeps.cpp` / `TfScriptModuleLoader`:

```python
t = Tf.Type.FindByName("UsdGeomXform")   # loads UsdGeom lazily via TfScriptModuleLoader
assert not t.isUnknown, "moduleDeps registration likely broken (pxr. vs pxr_lte. mismatch)"
```

If the `pxr.` → `pxr_lte.` rewrite in `genModuleDepsCpp.cmake`/`patchModuleDeps.py` were broken, this lookup would silently return an unknown type instead of raising an import error, so it's worth checking explicitly rather than relying on `from pxr_lte import UsdGeom` succeeding on its own.

You can also inspect a generated `moduleDeps.cpp` directly to confirm the registration prefix:

```bash
grep -n RegisterLibrary build-lte-sameproc/pxr/base/gf/moduleDeps.cpp
# should show: RegisterLibrary(TfToken("gf"), TfToken("pxr_lte.Gf"), reqs);
```

### 2. Same-process dual-namespace coexistence

This is the actual point of the whole feature — a standard `pxr` (e.g. installed via `pip`) and the custom `pxr_lte` build must load and operate together in one process without symbol collisions:

```python
from pxr import Usd as StdUsd
from pxr_lte import Usd as CustomUsd

std_stage = StdUsd.Stage.CreateInMemory()
custom_stage = CustomUsd.Stage.CreateInMemory()

assert StdUsd.Stage is not CustomUsd.Stage   # distinct types, no collision
```

### 3. Existing experiment test scripts

`experiment/ns_dual/` has ready-to-run scripts covering a broader module sweep (Tf, Gf, Vt, Sdf, Usd, UsdGeom, UsdShade, Kind, Ar) and layer/export operations:

```bash
python experiment/ns_dual/test_pxr_lte_only.py        # pxr_lte only, no pip pxr required
python experiment/ns_dual/test_dual_usd_sameproc.py   # both pxr and pxr_lte together
```

Both hardcode paths to `~/work/dist-usd-lte-v26.05` and `~/work/dist-tbb-reldeb` (edit `CUSTOM_USD_ROOT`/`TBB_ROOT` at the top if yours differ). Note: `test_dual_usd_sameproc.py` has a pre-existing, harmless assertion on `Tf.Token` (not a real attribute of either `pxr.Tf` or `pxr_lte.Tf`) that prints `FAILED` for that one sub-check but does not affect the script's overall pass/fail result — this is a bug in the test script itself, not a namespace-patching regression.

## Technical Details

### What Gets Patched

1. **Python source files** (`__init__.py`, etc.):
   - `from pxr import` → `from pxr_lte import`

2. **C++ moduleDeps.cpp files**:
   - `TfToken("pxr.Tf")` → `TfToken("pxr_lte.Tf")`
   - This ensures `TfScriptModuleLoader` registers modules with the correct package name

### Why moduleDeps.cpp Patching is Needed

`moduleDeps.cpp` registers each library's Python module dependencies with `TfScriptModuleLoader` using a hardcoded `pxr.` prefix:

```cpp
TfScriptModuleLoader::GetInstance().
    RegisterLibrary(TfToken("tf"), TfToken("pxr.Tf"), reqs);
```

Without patching, importing `pxr_lte.Usd` would fail because the loader would look for `pxr.Tf` instead of `pxr_lte.Tf`.

### Two Code Paths in v26.05

As of v26.05, most libraries no longer check in a `moduleDeps.cpp` source file — it's generated at configure time from `cmake/macros/moduleDeps.cpp.in` via `cmake/macros/genModuleDepsCpp.cmake` (this is the template-based approach that used to be dev-branch-only in earlier releases). A small number of libraries still check in their own `moduleDeps.cpp`. Both paths are patched:

1. **Generated case** (the common one): `genModuleDepsCpp.cmake` accepts a `packageName` argument. When it differs from `pxr`, the generator rewrites `TfToken("pxr.` to `TfToken("${packageName}.` in the generated file before writing it out. `Public.cmake` passes `-DpackageName=${PXR_PYTHON_PACKAGE_NAME}` when invoking the generator.
2. **Checked-in case** (legacy, now rare): handled the same way as v24.11 — `Public.cmake` detects `moduleDeps.cpp` in `PYTHON_CPPFILES`/`PYMODULE_CPPFILES` and runs `patchModuleDeps.py` on it at build time.

## Files Modified

- `cmake/defaults/Options.cmake` - Added `PXR_PYTHON_PACKAGE_NAME` option
- `cmake/macros/Private.cmake` - Added Python source file patching
- `cmake/macros/Public.cmake` - Added PYTHON_CPPFILES/PYMODULE_CPPFILES moduleDeps.cpp patching, and passes `PXR_PYTHON_PACKAGE_NAME` through to `genModuleDepsCpp.cmake` for the generated-file case
- `cmake/macros/genModuleDepsCpp.cmake` - Rewrites the `pxr.` registration prefix in generated `moduleDeps.cpp` when a custom package name is set
- `cmake/macros/patchModuleDeps.py` - Helper script for patching checked-in `moduleDeps.cpp` files

## Troubleshooting

### Import Error: "No module named 'pxr'"

If you see an error like `ModuleNotFoundError: No module named 'pxr'` when importing `pxr_lte`, it means the Python source files weren't properly patched. Check that:
1. The `PXR_PYTHON_PACKAGE_NAME` CMake option is set
2. The build completed successfully with "Patching __init__.py for custom package name" messages

### Import Error: Module dependency issues

If you see errors about missing modules like `pxr.Tf`, it means the moduleDeps.cpp files weren't properly patched. Check that:
1. The `patchModuleDeps.py` script exists in `cmake/macros/`
2. The build shows "Patching moduleDeps.cpp for custom package name" messages
3. The patched files contain `pxr_lte.` instead of `pxr.`

### DLL Not Found (Windows)

Use `os.add_dll_directory()` to add the library paths before importing:
```python
import os
os.add_dll_directory(r'C:\path\to\dist-usd-lte-v26.05\lib')
os.add_dll_directory(r'C:\path\to\dist-usd-lte-v26.05\bin')
os.add_dll_directory(r'C:\path\to\tbb\bin')
```
